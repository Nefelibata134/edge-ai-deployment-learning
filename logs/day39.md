## 稳定性验收为什么不能只看进程

`ActiveState=active` 和 `NRestarts=0` 只能说明 systemd 认为进程仍然存在，不能证明摄像头正在输出可解码帧。视频程序可能处于以下故障状态：

- 主进程存活，但 Argus 或 GStreamer 不再产生帧。
- RTSP TCP 连接仍存在，但上游不发送有效视频。
- 推理线程阻塞，服务没有退出却不再更新结果。

因此本次稳定性判断同时使用三层信号：

1. systemd 服务持续 `active/running`，PID 和重启计数符合预期。
2. watchdog 时间戳持续推进，证明运行时仍在主动报告健康。
3. 行缓冲运行日志持续出现完整帧记录，证明有真实帧进入检测链路。

用户能够解释：`NRestarts=0` 不足以证明健康，因为进程可能存在但摄像头没有真实帧流入。

## 自动化工具

正式项目新增了以下运维能力：

- `collect_service_soak.py`：按固定间隔采集 systemd、帧进度、RAM、spool、磁盘和 `tegrastats`。
- `summarize_service_soak.py`：计算覆盖率、资源趋势、卡帧窗口和最终运行指标，并执行阈值验收。
- `finalize_service_soak.sh`：优雅停止当前代次、保存最终原子指标、生成报告并恢复服务。
- `inject_service_crash.py`：向主进程发送 SIGKILL，验证 systemd 监督恢复。
- RTSP 故障注入脚本：停止并重启本地 H.264 replay，验证输入源恢复。

原始日志、事件证据和视频保留在 Git 忽略目录中；公开仓库只提交方法、摘要、结论和限制。

## 排错记录

### 1. 输出目录归属恢复错误

首次 90 秒 collector 运行报错：

```text
NameError: name 'files' is not defined
```

原因是 root 运行后的归属恢复循环缩进错误，引用了不在作用域中的 `files`。修复后增加测试，确认父目录和文件都会恢复为调用用户，避免生成 root 所有的实验产物。

### 2. systemd 版本参数不兼容

Jetson Ubuntu 22.04 使用 systemd 249，不识别较新版本的：

```text
systemctl kill --kill-whom=main
```

兼容实现会先检查帮助输出，再选择 systemd 249 支持的 `--kill-who=main` 或新版本的 `--kill-whom=main`。两种分支都有自动化测试。

### 3. 指标时间窗口不一致

60 分钟 collector 精确覆盖一小时，但最终运行指标中的 278,089 帧约对应 154.5 分钟，因为服务代次早于 collector 启动且在结束后才被优雅终止。

处理方式不是丢弃结果，而是明确区分：

- 121 个外部样本是准确的一小时稳定性窗口。
- 最终运行指标是更长进程代次的吞吐和延迟证据。
- 汇总器会估算进程代次时长；两个窗口相差超过 10% 时写入说明，但不把它误判成运行失败。
- 后续基线应在 collector 前立即重启服务，并在采集完成后立刻 finalize。

验收不止看新 PID。新代次还必须创建新 session、重新报告 ready，并通过后续真实帧推进 watchdog，才算恢复成功。

## 复盘

- 稳定性不是“程序运行了多久”，而是服务、输入、处理进度、资源和输出都持续满足契约。
- 短时冒烟可以廉价发现脚本和权限错误，避免浪费长时间实验。
- 故障恢复必须观察恢复后的业务进度，而不是只观察 socket 或进程重新出现。
- 报告必须明确采样窗口和指标代次，不能因为数字看起来合理就混用。
- 当前结果支持项目 v1 的单机一小时稳定性声明，但不支持多日耐久、物理断相机、磁盘耗尽或远程弱网恢复声明。
