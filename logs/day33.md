## 事件数据流

```text
IMX219 / replay frame
    -> GStreamer capture and bounded queue
    -> YOLOX TensorRT detector
    -> ByteTrack
    -> Track[]
    -> SafetyEventEngine
       -> ROI intrusion
       -> finite line crossing
       -> timestamp dwell
    -> event log and latency counters
    -> asynchronous annotated video writer
```

事件模块只消费当前帧上下文和 `Track[]`，不修改检测器输出，也不参与 ByteTrack 关联。这样事件规则变化不会改变模型精度或轨迹 ID，检测、跟踪和业务规则可以独立测试。

## 规则语义

### 轨迹锚点

规则使用检测框底边中心，而不是边界框中心。对人员安全区域而言，底边中心更接近脚与地面的接触位置，能减少“上半身进入区域但实际站立位置仍在外部”的误判。

### ROI 闯入

- 区域使用归一化坐标，能够适配 720p 和 1080p 输入。
- 点进入多边形并连续满足确认帧数后，只触发一次闯入事件。
- 离开后再次进入可以建立新的事件周期。

### 有限警戒线越线

- 先用叉积符号判断锚点位于线的哪一侧。
- 再验证前后运动线段是否与配置的有限警戒线相交。
- 不能只判断无限直线两侧，否则在警戒线端点之外经过也会误触发。
- 可配置任意方向、负侧到正侧或正侧到负侧。

### 停留

- 使用视频 PTS 计算真实停留时间，不使用帧数估算。
- 丢帧或输入 FPS 波动时，3 秒仍表示时间戳相差 3 秒。
- 事件状态允许最多 3 帧的短暂观测空档，超过后重新计时。

### 状态重置

输入流代次变化、时间线回退或显式重置时，事件状态必须清空，避免新视频中的目标继承上一段视频的闯入、停留或越线状态。

## IMX219 真实验证

### 全画面 ROI 与停留

第一次使用右半画面 ROI 时事件数为 0。系统本身正常运行，但轨迹底边中心没有满足指定区域和线段条件。随后使用全画面 ROI 做受控验证：

```text
event=roi_intrusion frame=37 pts_ms=1233.333 track_id=2
event=dwell frame=127 pts_ms=4233.333 track_id=2
```

两个事件相差正好 3,000 ms，符合 `dwell=3s`。frame 125 曾短暂出现 `tracks=0`，但观测空档没有超过事件规则的 `max_gap_frames=3`，因此停留状态被保留并在 frame 127 正确触发。

这里需要区分两层容错：

- `track_buffer=30` 负责 ByteTrack 丢失轨迹的 ID 恢复。
- `max_gap_frames=3` 负责事件状态对短暂轨迹观测空档的容忍。

### 有限警戒线

使用画面中央的归一化竖线完成一次真实穿越：

```text
event=line_crossing
frame=131
track_id=2
class_id=0
anchor=0.516,0.992
direction=positive-to-negative
```

## 审计视频

异步视频输出新增：

- 橙色 ROI 边界。
- 紫色有限警戒线。
- 跟踪框、类别、置信度、稳定 ID 和底边中心锚点。
- 保留约 1.5 秒的 `ROI INTRUSION`、`LINE CROSSING` 和 `DWELL` 标签。
- 输出队列丢弃旧帧时，将该帧携带的事件转交给下一帧，避免日志有事件但视频证据丢失。

全画面 ROI 测试中视频编码队列曾丢弃 25 个旧输出帧，但输入测量阶段丢帧为 0，检测、跟踪和事件判断没有被编码阻塞。将输出队列容量提高到 64 后，越线测试写出 240/240 帧。

## 复盘

- 检测和跟踪只回答“有什么、是谁”，事件状态机才把连续轨迹转化为可执行的安全语义。
- 合成轨迹适合验证确定性边界，真实视频负责验证坐标、时间戳、摄像头和输出链路，两者不能互相替代。
- 本次事件层 P95 只有 0.006 ms，业务规则没有成为 30 FPS 链路的性能瓶颈。
- 审计视频必须同时显示规则边界、锚点和事件标签，否则只能证明程序输出过事件，不能判断触发是否合理。
