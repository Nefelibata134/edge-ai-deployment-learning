## 事件证据数据流

```text
SafetyEventEngine
    -> SafetyEvent
    -> EventRecord
       -> schema version
       -> session/source/stream generation
       -> deterministic event ID
       -> event type/rule/track/class/frame/PTS/anchor
    -> atomic snapshot
    -> bounded pre-event frame ring
    -> collect post-event shared frame references
    -> bounded background encoding queue
    -> verified and atomically renamed MP4
    -> append-only JSONL journal
```

JSONL 记录只在相应证据文件成功关闭和校验后发布。这样下游读取到记录时，截图和片段路径已经真实存在。

## JSONL 协议

每条记录包含：

- `schema_version`：协议版本，便于后续兼容升级。
- `event_id`：事件稳定标识，用于幂等去重。
- `session_id`：区分不同程序运行，避免重启后复用的轨迹 ID 被误认为同一事件。
- `source_id`：标识 CSI 或文件输入来源。
- `stream_generation`：区分同一进程中的输入流重连代次。
- `recorded_at_utc`：用于跨系统日志关联。
- `event_type`、`rule_id`、`track_id`、`class_id`。
- `frame_sequence`、`pts_ns`、归一化 `anchor` 和越线方向。
- `evidence.snapshot_path` 与 `evidence.clip_path`。

事件 ID 由上述稳定身份字段计算，而不是依赖内存地址或随机顺序。同一事件在当前进程重复提交和重新打开现有 JSONL 后都不会再次追加。

## 原子证据写入

截图和视频先写入临时文件，完成后检查文件存在且大小非零，再原子改名为最终路径。写入顺序为：

```text
生成证据 -> 校验证据 -> 原子改名 -> 写入 JSONL
```

如果在证据完成前直接发布 JSONL，程序崩溃后会留下指向空文件或不存在文件的悬空记录。

## 有界前置缓存

IMX219 实际处理帧为 1280x720 BGR，每帧占用：

```text
1280 x 720 x 3 = 2,764,800 bytes
```

30 FPS 下保留事发前 2 秒共 60 帧：

```text
2,764,800 x 60 = 165,888,000 bytes ≈ 158.2 MiB
```

缓存使用固定容量环形结构，持续淘汰最旧帧，不能为了保留历史画面无限增长。多个事件片段共享不可变帧引用，避免重复复制相同像素数据；完成采集后的片段通过有界后台队列编码。

## IMX219 真实验证

### 第一次：规则没有命中

目标被稳定识别为 `class 0`，但边界框底边中心约为 `y=0.99`，配置的 ROI 下边界为 `0.98`，因此事件数为 0。空 JSONL 是正确输出，系统没有为未发生的事件伪造证据路径。

这次结果再次验证事件区域判断使用脚点语义。画面中的上半身虽然处于 ROI 内，但底边中心不在区域内时，不能确认人员已经站入对应地面区域。

### 第二次：同步编码暴露性能缺陷

将 ROI 扩展为完整画面后，截图、JSONL 和 7 个事件片段均成功生成，但同步 `VideoWriter::write()` 阻塞了实时线程：

| 指标 | 同步编码结果 |
| --- | ---: |
| 测量帧数 | 240 |
| 输入丢帧 | 567 |
| 有效 FPS | 8.898 |
| 事件 I/O 平均延迟 | 100.475 ms |
| 事件 I/O P95 | 107.140 ms |
| 端到端 P95 | 166.714 ms |
| 唯一轨迹 ID | 7 |
| 事件数 | 7 |

同步编码形成了反馈链：

```text
编码阻塞
  -> 采集队列丢帧
  -> ByteTrack 轨迹断裂并分配新 ID
  -> 同一人员重复触发 ROI 事件
  -> 同时编码更多片段
  -> 阻塞进一步加重
```

功能测试虽然已经通过，但非功能性实时指标失败，因此不能把该版本视为完成。

### 第三次：有界异步编码

重构后，实时线程只负责标注当前帧、维护共享帧引用和提交完成片段；后台线程负责 OpenCV 编码、文件校验和原子改名。待编码片段数量受限，队列满时明确跳过片段而不是阻塞推理。

真实对照结果：

| 指标 | 同步编码 | 异步编码 |
| --- | ---: | ---: |
| 输入丢帧 | 567 | 0 |
| 有效 FPS | 8.898 | 30.050 |
| 事件 I/O 平均延迟 | 100.475 ms | 2.625 ms |
| 事件 I/O P95 | 107.140 ms | 3.797 ms |
| 端到端 P95 | 166.714 ms | 16.366 ms |
| ROI 事件 | 6 | 1 |
| 停留事件 | 1 | 1 |

异步版本最终产生 2 条 JSONL 记录，两条都属于稳定的 `track_id=2`：

- `roi_intrusion`：截图和片段均存在且非空。
- `dwell`：截图和片段均存在且非空。

后台剩余录像在退出时用约 491 ms 完成编码和校验。它增加的是关闭耗时，不进入实时帧延迟；等待完成可以避免损坏的临时视频和悬空 JSONL 路径。

## 用户修改验证

在 10 FPS 的确定性片段测试中，将前置时长从 0.2 秒改为 0.1 秒，并将期望片段帧数从 5 改为 4：

```text
事前 0.1 秒 = 1 帧
触发帧       = 1 帧
事后 0.2 秒 = 2 帧
总计         = 4 帧
```

修改后测试按预期输出 `clip_frames=4` 和 `status=PASS`。恢复正式配置后重新得到 `clip_frames=5`，工作树保持干净。

## 遇到的问题

- ROI 下边界为 0.98 时，人员框底边中心约为 0.99，事件规则正确地没有触发。
- CLI 内部支持 `class_id=-1` 通配符，但整数解析器最初拒绝负号；修复后只接受 `-1` 或非负类别 ID。
- 同步事件片段编码导致严重丢帧和轨迹碎片，通过共享帧引用、有界任务队列与后台编码解决。

## 复盘

- 事件输出不仅是打印一行文字，而是一份需要身份、时间、来源、证据和幂等语义的系统契约。
- 测试文件生成只能证明功能路径可用，真实摄像头集成测试才能发现同步编码造成的实时性崩溃。
- 实时系统必须同时检查平均值、P95、丢帧、队列、轨迹连续性和事件数量，单看 FPS 或文件是否存在都不够。
- 把慢 I/O 移到后台时仍需有界队列和明确降级策略，否则只是把阻塞问题换成无界内存问题。
